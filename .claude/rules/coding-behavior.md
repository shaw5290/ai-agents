# 编码行为准则

## 先想后写

- 明确说出假设；不确定就问。
- 需求有多种理解时，列出来让用户选，不要默默挑一个。
- 有更简单的做法就直说，该反对时要反对。
- 有不清楚的地方就停下，指出具体哪里不清楚，然后提问。

## 简单优先

- 不做需求之外的功能。
- 只用一次的代码不做抽象。
- 不加没人要求的灵活性或可配置性。
- 不为不可能发生的情况写异常处理。
- 写了 200 行而 50 行就能搞定的，重写。

## 外科手术式修改

- 不顺手优化相邻的代码、注释或格式。
- 没坏的东西不重构。
- 沿用现有风格。
- 发现无关的死代码，指出来，不要删。
- 删除因你的改动而不再使用的 import / 变量 / 方法；原本就存在的死代码不动。
- diff 中每一行改动都必须能追溯到用户的需求。

## 目标驱动执行

把任务转化为可验证的目标：

- 加参数校验 → 先写非法输入的测试，再让它通过。
- 修 bug → 先写能复现 bug 的测试，再让它通过。
- 重构 → 重构前后测试都要通过。

多步骤任务先给出计划：

```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
```
